# UI strings and languages

This page explains how the app's interface text works in English and Afrikaans, and how to add strings or a new language. The 36 documents are content, not UI strings. Their translation workflow is in `docs/build-plan.md` Part A6.

## Locales

`LOCALES` in `src/i18n/locales.ts` is the only list of languages. Everything else derives from it:

- `enabled: true` means the locale is routed and built. Only `en` and `af` are enabled.
- `ENABLED_LOCALES` is `['en', 'af']`. The type `Locale` is `'en' | 'af'`. `LocaleCode` is any of the 11 codes. `src/lib/paths.ts` re-exports `ENABLED_LOCALES` under the same name. No other file exports a `LOCALES`, so an auto-import cannot pick the wrong list.
- `DEFAULT_LOCALE` is `en`. English URLs have no prefix, other locales get `/<code>/`.
- `status` describes the documents: `complete` (English), `partial` (Afrikaans, machine translated, not yet reviewed), `planned` (the other nine).
- `uiDictionary: true` means `src/i18n/<code>.json` exists with the full key set. A test checks that the file exists exactly when this flag is set, and that the file is registered in `index.ts`. Every dictionary with this flag gets all parity and text-rule tests, even while `enabled` is still `false`.
- `hreflang` (`af-ZA`) is also used for `<html lang>` and `Intl.PluralRules`.

## Using strings

In `.astro` frontmatter:

```ts
import { useTranslations } from '../../i18n';
const tr = useTranslations(locale);
tr('nav.skipLink'); // "Skip to main content"
tr('nav.next', { title: doc.title }); // "Next: Tax and SARS"
tr('search.results', { count: 3 }); // "3 results"
```

Or directly: `t(locale, 'nav.skipLink')`.

`t()` returns plain text. Render it with `{…}` in Astro or with `textContent`, never with `set:html` or `innerHTML`, because parameter values are inserted without escaping.

Keys are dot paths, typed from `en.json`. A key that does not exist fails `pnpm typecheck`. Build dynamic keys from typed unions, for example `` t(locale, `nav.sections.${section}.name`) `` where `section` is one of the section ids.

### Parameters are typed

`t`, `useTranslations` and `createTranslator` check the parameters of each key:

```ts
t(locale, 'nav.next'); // type error: needs { title }
t(locale, 'nav.next', { name: 'x' }); // type error: the parameter is called title
t(locale, 'search.results', { count: '3' }); // type error: count must be a number
```

JSON imports have no literal string types, so TypeScript cannot read `{title}` out of `en.json` itself. The names live in a generated `interface ParamNames` block in `src/i18n/index.ts`, between `// @generated-start param-names` and `// @generated-end param-names`. A test in `tests/unit/i18n.test.ts` fails when the block is out of date. To regenerate it:

```sh
pnpm exec cross-env I18N_UPDATE_TYPES=1 vitest run --project unit tests/unit/i18n.test.ts -t ParamNames
pnpm exec prettier --write src/i18n/index.ts
```

Keys without placeholders accept an optional params object, but `count` must still be a number.

A key union needs every placeholder of every key in the union. `` t(locale, `doc.hiddenFor.${reason}`) `` with `reason: 'sole-prop' | 'businessTypes'` fails to compile without `{ types }`, because `doc.hiddenFor.businessTypes` uses it. Pass the params for the whole union; keys without that placeholder ignore them. A union of `'sole-prop' | 'pty'` needs no params.

The one escape hatch is the wide `TranslationKey` type, for example a key read from data and cast with `as TranslationKey`. Its params are optional and not checked, and a missing placeholder only stays in the text and warns in dev. Use a narrower type wherever you can.

### Accessible names for repeated controls

When a control appears many times on one page (copy-link buttons in the glossary, "Read" on every step card, copy buttons on prompts), use the short key for the visible text and the `…Named` or `…To` key for `aria-label`, so a screen reader list of buttons is not a list of identical names:

```astro
<button aria-label={tr('glossary.copyLinkTo', { term: entry.term })}>{tr('glossary.copyLink')}</button>
```

Pairs include `doc.copyLink`/`doc.copyLinkTo`, `glossary.copyLink`/`glossary.copyLinkTo`, `sources.copyLinkTo`, `doc.hiddenShow`/`doc.showHiddenNamed`, `doc.showHiddenSections`, `doc.show`/`doc.showNamed`, `templates.open`/`templates.openNamed`, `myPath.read`/`myPath.readStep`, `myPath.markDone`/`myPath.markDoneNamed`, `myPath.markNotDone`/`myPath.markNotDoneNamed`, `prompts.copy`/`prompts.copyNamed`, `prompts.fillFromProfile`/`prompts.fillFromProfileNamed`, `prompts.undoFill`/`prompts.undoFillNamed`, `prompts.showFull`/`prompts.showFullNamed`, `prompts.showLess`/`prompts.showLessNamed`, `trust.fact.source`/`trust.fact.sourceNamed`, `common.close`/`common.closeNamed`, `common.dismiss`/`common.dismissNamed`, `home.businessTypes.openType`.

Every `prompts.…Named` button name (`copyNamed`, `fillFromProfileNamed`, `undoFillNamed`, `showFullNamed`, `showLessNamed`) takes `{n}` and `{title}` in the same order ("Copy prompt 2: Logo brief"), so the names in one prompt block follow one pattern. The status message `prompts.copiedNamed` ("Prompt 2 copied") takes only `{n}`.

The name of a "Remove line" button comes from the text the user typed. A new line is still empty, so use the numbered key when the text is blank, otherwise several buttons would all be called "Remove line:":

```ts
const name = description.trim()
  ? tr('templates.removeLine', { description })
  : tr('templates.removeLineEmpty', { n: index + 1 });
```

The same applies to `templates.privacy.removeListItem` and `templates.privacy.removeListItemEmpty`.

### Client scripts

Custom elements cannot import the whole dictionary without adding weight. Serialise only the groups they need:

```astro
---
import { pick } from '../../i18n';
const strings = pick(locale, ['search', 'prompts']);
---
<st-search data-locale={locale} data-strings={JSON.stringify(strings)}></st-search>
```

```ts
import { createTranslator, type Dict } from '../../i18n';
const strings = JSON.parse(this.dataset.strings!) as Pick<Dict, 'search' | 'prompts'>;
const tr = createTranslator(locale, strings);
tr('search.results', { count: hits.length });
```

`createTranslator` only accepts keys from the picked groups. A client script that imports only `createTranslator` does not bundle the dictionaries: Vite tree-shakes them. A minified probe build was about 3.8 KB raw and 1.4 KB gzip, with no dictionary strings in it.

### Placeholders

- Written as `{name}`: a letter, then letters, digits or `_`.
- Values are inserted with `String(value)`. Numbers are not regrouped, so years and counts stay as typed. Format amounts first with `formatRand` or `formatNumber`, and dates with `formatDate`.
- A missing parameter leaves `{name}` in the text and warns in dev.
- Every language must use exactly the same placeholder names per key. Word order may change. For plural keys the names are compared across all forms together, so a language may leave `{count}` out of one form (for example "Een resultaat").
- Figures that can change (the VAT rate, a year, a threshold, the number of questions) are always parameters: `"VAT ({rate}%)"`, `"Three numbers that changed in {year}"`. A test fails when an English string contains a digit outside a placeholder. The only exception is the part name "Part A2".

### Plurals

A plural value is an object whose keys are CLDR plural categories (`zero`, `one`, `two`, `few`, `many`, `other`). `other` is required.

```json
"results": { "one": "{count} result", "other": "{count} results" }
```

- Pass `count` as a number: `t(locale, 'search.results', { count: 1 })`. The type requires it.
- The form is chosen with `Intl.PluralRules(hreflang)`. A missing category falls back to `other`.
- Each locale must include every category its language needs (a test reads them from `Intl.PluralRules`), and the same categories as English. English and Afrikaans both use `one` and `other`.
- A group object must never have a key called `other`. That key marks a plural.

### Fallback

If a key is missing in a non-English dictionary, or has the wrong shape (a string where English has a plural), `t` and `pick` use English. In dev, and in tests, `console.warn` names the key. Production builds are silent. The parity test makes this a safety net, not a normal state.

## Formatting

All formatters take a locale for symmetry. Numbers and amounts use one format in every language, because Afrikaans keeps numbers byte-identical to English.

| Function                                   | Example             |
| ------------------------------------------ | ------------------- |
| `formatDate('en', '2026-09-13')`           | `13 September 2026` |
| `formatDate('af', '2026-03-01')`           | `1 Maart 2026`      |
| `formatDate('en', '2026-09-13T22:30:00Z')` | `14 September 2026` |
| `formatRand('en', 1234.56)`                | `R 1 234.56`        |
| `formatRand('af', -50)`                    | `-R 50.00`          |
| `formatNumber('af', 2300000)`              | `2 300 000`         |
| `formatNumber('en', 1.23456)`              | `1.235`             |

- **Rand**: `R`, a space, thousands grouped with spaces, `.` before the cents, always two decimals, rounded half away from zero (1.005 becomes 1.01). Both spaces are no-break spaces (U+00A0) so an amount never wraps across lines on a printed invoice. Negative amounts are `-R 50.00`. Amounts above `MAX_RAND_AMOUNT` (`Number.MAX_SAFE_INTEGER / 100`, about R90 trillion) throw `RangeError`, because cents are no longer exact. Tests build the expected strings with U+00A0.
- **Numbers**: same grouping and decimal mark. No trailing zeros, and at most three decimals (`DEFAULT_MAX_FRACTION_DIGITS`) unless you pass `maximumFractionDigits`. Rounding is half away from zero, so `1.23456` shows as `1.235`, `0.0006` as `0.001` and `0.0004` as `0`. For small rates and ratios, pass `maximumFractionDigits` (`formatNumber('en', 0.00012, { maximumFractionDigits: 5 })` is `0.00012`). `minimumFractionDigits` on its own raises the maximum to match, so `{ minimumFractionDigits: 4 }` shows four decimals. A value that rounds to zero, and minus zero, show as `0`.
- **Dates**: month names and word order come from the dictionary (`date.months.1` to `date.months.12`, `date.format`), so the output does not depend on the ICU data of the browser. Input is `YYYY-MM-DD`, or an ISO timestamp with `Z` or an offset (`+02:00` or `+0200`, up to ±14:00), which is shown as the calendar day in South Africa (UTC+02:00, no daylight saving). Years run from 1900 to 9999, both in the input and in the day shown in South Africa. There is no fallback output: anything else throws `RangeError`. That includes impossible dates in either form (`2026-02-30`, `2026-02-30T10:00:00Z`), hours from 24 up, a lower-case `z`, a missing time zone, `0100-03-01` and `9999-12-31T22:00:00Z` (which would be year 10000 in South Africa).
- Non-finite numbers throw `RangeError`.

## Routes

Pages live in `src/pages/[...locale]/…`.

```ts
import { localeStaticPaths } from '../../lib/i18n-routes';
export const getStaticPaths = () => localeStaticPaths();
// [{ params: { locale: undefined }, props: { locale: 'en' } },
//  { params: { locale: 'af' }, props: { locale: 'af' } }]
```

Routes with more params combine these with their own entries.

Both helpers, and `href`, `localeFromPath` and `routeFromPath` in `paths.ts`, normalise `base` with `basePath()`. `/business-toolkit`, `business-toolkit/` and `/business-toolkit/` give the same result, and `''` means `/`. When you leave `base` out, the configured `BASE_URL` is used.

- `alternateUrls(route, availableLocales, site, base?)` returns `{ hreflang, href, locale }[]` with absolute URLs for every available enabled locale, plus `x-default` pointing to English when English is available. Pass the locale-independent route (`core/register/` or `/core/register/`). A locale prefix on the route (`af/core/register/`) is removed, so it is never doubled. Query and hash are dropped. Unknown and disabled codes are ignored. Any path on `site` is ignored. These routes throw `RangeError`: a full URL (`https://…`, `mailto:…`), a protocol-relative URL (`//host/…`), and a route with a `.` or `..` segment, also percent-encoded (`../core/`, `%2e%2e/core/`), because `new URL` would resolve it differently for each locale.
- `switchLocaleUrl(current, targetLocale, base?)` returns the same page in the other language as a path that starts with the base, and keeps the query string and hash. The language switcher uses it for plain links. It never redirects.

`current` accepts exactly these forms:

| `current`                                                                            | Read as                                                                 |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| A string that starts with `/`: `location.pathname + location.search + location.hash` | A path. Query and hash are kept                                         |
| A string that starts with `//`, for example `//core/register/`                       | A path, never a host. Repeated slashes are collapsed: `/core/register/` |
| A string that starts with `http:` or `https:` (any case): `location.href`            | A full URL. The host is ignored                                         |
| A `URL` object: `new URL(location.href)`                                             | A full URL. The host is ignored                                         |
| A string with another scheme (`mailto:`, `javascript:`)                              | Throws `RangeError`                                                     |
| A relative path (`core/register/`) or `''`                                           | Throws `RangeError`                                                     |
| A string with a backslash (also `%5c`), a tab or a line break                        | Throws `RangeError`                                                     |
| A path with a `.` or `..` segment, also `%2e` (`/af/../../evil/`)                    | Throws `RangeError`                                                     |

`alternateUrls` and `switchLocaleUrl` share one guard, so both reject the same shapes: `new URL` treats `\` as `/` and drops tabs and line breaks, and it resolves `..`, so either would otherwise send one locale to a different page from another. A full URL string and a `URL` object are normalised by `new URL` before the dot-segment check, so `https://x.test/a/../b/` arrives as `/b/` and is accepted.

Repeated slashes anywhere in the path are collapsed before the locale is read. A protocol-relative string such as `//example.com/business-toolkit/` is read as a path, so pass `location.href` or a `URL` when you have a full address.

## Text rules (enforced by `tests/unit/i18n.test.ts`)

- Every dictionary with `uiDictionary: true` has exactly the English keys. Missing and extra keys both fail, with a list of each.
- No empty strings, no leading or trailing spaces, no double spaces, no line breaks.
- No straight quotes or apostrophes (`"` and `'`). Use “ ” and ’. Afrikaans writes ’n with U+2019. This keeps strings safe in HTML attributes and consistent in print.
- No exclamation marks and no `...`. Use the single character `…` for "loading" states.
- Braces appear only as `{param}` placeholders.
- English strings contain no figures outside placeholders (see Placeholders). Digits are byte-identical to English per key.
- Fixed names stay verbatim (SARS, CIPC, POPIA, Pty Ltd, BizPortal, eFiling, PayShap, PAYE, PDF, JavaScript).
- Fixed Afrikaans terms are checked outside text in “quotes”. Quoted text is a literal, for example the legal words “Tax Invoice”, and stays in English.
- Length: every English string of at most 24 characters counts as a label. The translation fails when it is more than 1.6 times the English length and at least five characters longer. Exceptions are listed per locale in `LABEL_LENGTH_EXCEPTIONS` in the test, each with a reason. A new language starts with none. A test fails when one of a locale's own exceptions is no longer needed. The design allows about +25% for all text.

### Strings that mirror content headings

Some UI strings repeat a heading from the markdown documents. The markdown is the source of truth: the English string must match the English heading exactly, and the Afrikaans string must match the heading in `docs/rsa-business-toolkit-af/`. If a heading changes, change the string in the same commit, and the other way round.

| Key                                          | English heading (`docs/rsa-business-toolkit/`)                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `checklist.title`                            | `05 Look it up/02-master-checklist.md` H1 "Master checklist"                                    |
| `checklist.keyToShortWords`                  | same file, "Key to the short words"                                                             |
| `checklist.parts.a`, `.a2`, `.b`, `.c`, `.d` | same file, the "Part A" to "Part D" headings                                                    |
| `doc.wordsUsed`                              | the H2 "Words used in this file" in the documents that have one (it is not always the first H2) |

The Afrikaans content tree does not exist yet. Until it does, the Afrikaans strings are the agreed wording, and the Afrikaans headings must use it.

## AI disclosure and sources (`trust`)

`docs/build-plan.md` D5 and `docs/adr/0006-ai-disclosure-and-accuracy.md` require every content page to say that AI wrote it, to show when and how it was checked, and to list its sources. All strings for this live in the top-level `trust` group, so a page or component can `pick(locale, ['trust'])` in one go. They replace the earlier `doc.sourcesForPage` and `doc.verifiedOn`.

| Keys                                                                                       | Where it goes                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `trust.aiNotice.label` | Accessible name of the notice (`role="note"` or `<aside aria-label>`). At the top of the article header of every content page, before the first block. Not only in the footer |
| `trust.aiNotice.body` (`{date}`) | The notice text when only an AI has checked the page, on pages that have a "Sources for this page" section. `{date}` is `formatDate(locale, doc.verification.checkedOn)`. Wording from D5 |
| `trust.aiNotice.bodyNoPageSources` (`{date}`) | The same notice on pages without page-specific sources (start pages, the sources register), where "the sources below" would not be true. It points at the sources register instead, and says that official sources are marked there. It does not say the check was against official sources: about two thirds of the register is not official, and ADR 0006's accuracy review has not run yet |
| `trust.aiNotice.bodyHumanChecked` (`{reviewer}`, `{date}`) | The notice text when a named human expert has checked the page, on pages with a "Sources for this page" section. It names the reviewer instead of the AI and drops "No person has checked it yet" |
| `trust.aiNotice.bodyHumanCheckedNoPageSources` (`{reviewer}`, `{date}`) | The human-checked notice on pages without page-specific sources |
| `trust.aiNotice.link` | Link to `start/how-this-was-made`, at the end of the notice |
| `trust.status.aiChecked`, `trust.status.humanChecked` (`{reviewer}`) | A short verification status label in words, inside the notice, directly after the body. No date, and in Afrikaans no "Engelse teks": the notice body right before it and the explanation right after it both carry the date and the qualifier, and stating it three times in one header reads as anxious rather than careful. Never a colour or badge alone. Use the `humanChecked` status and body only for a named human expert (ADR 0006, point 5) |
| `trust.status.aiCheckedMeans`, `trust.status.humanCheckedMeans` (`{reviewer}`) | The explanation, directly after the status label and inside the notice, always visible. No tooltip or hover-only text. It explains the status and does not repeat the notice. `humanCheckedMeans` says that mistakes are still possible |
| `trust.sources.heading`, `trust.sources.count` (`{count}`)                                 | H2 of the "Sources for this page" section, near the end of the page before the pager, and its count                                                                                            |
| `trust.sources.officialLabel`, `trust.sources.supportsLabel`                               | Per entry: the "Official source" label (text, not colour only) and the label before what the source supports                                                                                   |
| `trust.sources.externalLink`, `trust.sources.externalLinkOther`                            | Visually hidden text on each external source link. Use `externalLinkOther` for sources that are not official, so the link does not imply more certainty than the source has                    |
| `trust.sources.actsHeading`                                                                | Subheading for the Acts and regulations in the same section                                                                                                                                    |
| `trust.sources.noPageSources`, `trust.sources.seeRegister`, `trust.sources.seeHowMade`     | The source note for pages without page-specific sources: the sentence, then two links, to `/sources/` and to `start/how-this-was-made`                                                         |
| `trust.fact.checked` (`{date}`), `trust.fact.source`, `trust.fact.sourceNamed` (`{title}`) | Inline label on threshold, fee and deadline callouts (home page, business-type hubs). `source` is the visible link text, `sourceNamed` its `aria-label`. `checked` names the AI ("AI-checked {date}", AF "KI-nagegaan op {date}"), so an inline callout never reads as a human check. It records the AI check of that one figure, so it does not change on a page whose notice names a human reviewer. Like the two short status labels (`trust.status.aiChecked`, `trust.status.humanChecked`) and `trust.templateRulesChecked`, it does not say "Engelse teks": it labels a figure, and `content:fidelity` keeps figures byte-identical between the trees. The notice body next to each of them states the English-text check |
| `trust.unverified.label`, `trust.unverified.body`                                          | Flag next to a fact that the accuracy review marked `unverifiable`: the label, then the sentence. Both visible                                                                                 |
| `trust.checklistReminder`                                                                  | Under the H1 of `/checklist/` and above every inline "Your checklist"                                                                                                                          |
| `trust.templateRulesChecked` (`{date}`)                                                    | On each template page, next to the required-items list                                                                                                                                         |

### Placement and order

These rules follow D5 in `docs/build-plan.md` (revised after WP-12b review pass 1) and the Document spec in B6.

1. The AI notice sits at the top of the article header, before the first block.
2. Inside the notice, in this order: the label, the body, the verification status (`trust.status.*`), its explanation (`trust.status.*Means`), then the link. The status and its explanation always sit directly next to the notice body. Never move them elsewhere on the page, to a tooltip or to the footer.
3. On Afrikaans pages the Afrikaans AI notice comes first. The machine-translation notice (`lang.mtNotice`) sits directly under it, in the same article header. B6 lists the MT banner in the article header, so this is its place in that header, not a second banner elsewhere.

On an Afrikaans page the three parts read as one sequence:
- the AI notice says that AI wrote the page, and who checked the **English text** and on which date;
- the status label is a short word or two, and its explanation says again that the check was on the English text;
- the machine-translation notice says that AI translated the page and that no person has checked the translation.

Every Afrikaans `trust.aiNotice.body*` and `trust.status.*Means` string says "Engelse teks", and none of them says that the facts "op hierdie bladsy" were checked, because that would claim the translation was checked. The two short status labels, `trust.status.aiChecked` and `trust.status.humanChecked`, deliberately do **not** carry the qualifier: the body directly above them and the explanation directly below them both state it, and saying it three times in one header reads as anxious rather than careful. Do not add it back — that was review pass 2's m3, and it would also revive two `LABEL_LENGTH_EXCEPTIONS` entries that are now correctly deleted.

A test in `tests/unit/i18n.test.ts` enforces both halves: it asserts `toContain('Engelse teks')` over the four `aiNotice.body*` strings and the two `*Means` strings, and asserts the two labels are exactly "KI-nagegaan" and "Deur {reviewer} nagegaan".

Tone, from the toolkit itself: short sentences, plain words, no jargon, no idioms, no exclamation marks. Readers may use English as a second language and may never have run a business.

## Add a key

1. Add it to `src/i18n/en.json` in the group for its area. Use camelCase for names, and the app's ids for keys that map to data (`business-types`, `sole-prop`, `pty-growing`). Never name a key `other` inside a group.
2. Add the same key to `src/i18n/af.json` (and every other file with `uiDictionary: true`).
3. If the key has `{param}` placeholders, or you changed them, regenerate `ParamNames` (see "Parameters are typed").
4. Run `pnpm exec vitest run --project unit tests/unit/i18n.test.ts` and `pnpm typecheck`.
5. Commit the English and Afrikaans change together with scope `i18n`.

To rename or remove a key, change every dictionary in the same commit, regenerate `ParamNames` and search `src/` for the old key.

## Add a language

Example: isiZulu (`zu`). Steps 1 and 2 go in one commit, and typecheck and test cleanly while `enabled` is still `false`.

1. **Dictionary**: copy `en.json` to `src/i18n/zu.json` and translate every value. Keep keys, placeholders, digits and plural categories. Add any plural categories the language needs (the test lists them). Translate `lang.names` and `date.months`, and set `date.format` word order.
2. **Register it**: in `src/i18n/locales.ts` set `uiDictionary: true` for `zu`. Keep `enabled: false` and `status: 'planned'`. In `src/i18n/index.ts` import the file and add it to `DICTIONARIES`:

   ```ts
   import zu from './zu.json';
   const DICTIONARIES: Readonly<Partial<Record<LocaleCode, DictTree>>> = { en, af, zu };
   ```

   `pnpm test` now checks `zu.json` for key parity, placeholders, plural categories, digits, text rules and label length. A new language has no label-length exceptions. If a label really cannot be shorter, add it under `zu` in `LABEL_LENGTH_EXCEPTIONS` in `tests/unit/i18n.test.ts`, with a reason. Run `pnpm typecheck` and `pnpm test` before you commit.

3. **Content mirror tree**: create `docs/rsa-business-toolkit-zu/` with the same file names as the English tree, with a style guide and terms file like the Afrikaans ones. Run `pnpm content:fidelity --lang zu` until it is clean, then `pnpm content:build`.
4. **Enable routing**: set `enabled: true` and the right `status` (`partial` until every document is reviewed). `Locale` now includes `'zu'`, so `t('zu', …)` typechecks. `astro.config.ts` picks up `i18n.locales` automatically, and `localeStaticPaths()` emits `/zu/` pages. Update the tests that pin the enabled list to `['en', 'af']` (`pnpm test` names them: for example "enables only English and Afrikaans", "builds the sitemap locale map", `localeStaticPaths` and `paths` "comes from src/i18n/locales.ts"). Tests that need a planned locale as an example take the first locale with `enabled: false`, so they keep working.
5. **Sitemap**: `sitemapLocales()` adds `zu: 'zu-ZA'` automatically. Check `dist/sitemap-0.xml` after `pnpm build`.
6. **Check**: `pnpm gate:fast`, then the language switcher, `<html lang="zu-ZA">`, hreflang links and the machine-translation notice on a few pages.

Fonts already include latin-ext, so Tshivenḓa letters (ḓ ḽ ṅ ṋ ṱ) render.

## Numbers, codes and URLs stay verbatim

In UI strings and in documents, never translate or reformat:

- digits, percentages and rand amounts (`R2.3 million` becomes `R2.3 miljoen`: the figure stays, the word changes);
- form codes and references (ITR12, ITR14, IRP6, EMP201, EMP501, VAT101, VAT264, SAPS 601, CoR 14.3, CoR 40.5, R638, R146);
- URLs, email addresses and domain names;
- act names (`Companies Act 71 of 2008`).

Pass values in through `{param}` placeholders rather than writing them into dictionary strings, so they come from the same data in every language.
